Q1

Carrying state across Realtime sessions

First, what a "session" actually is

This is the concept everything else in Q1 rests on, and it is the one most people get wrong.

A Realtime session is a WebSocket connection to OpenAI. The conversation history for that call lives on OpenAI's servers, bound to that specific connection. Your code does not hold it. You cannot query it. And critically: there is no "resume session" API. When the socket closes, that accumulated history is not archived somewhere for later. It is gone.

So when a call flow moves from one AI Agent block to the next and the next block opens its own session, the new session does not start with less context. It starts with none. A brand new model instance that has never heard of this caller.

The distinction that unlocks this

The word "context" is doing two different jobs, and separating them is the whole answer.

Conversation memory is the model's running history. It lives inside the session and dies with it. Application state is what your business actually needs to know: which field is being captured, what validated, whether the caller confirmed it. That can live wherever you decide to put it.

The mistake is treating them as the same thing and therefore trying to preserve the session. The fix is to stop caring about the session at all.

The architecture, drawn by lifetime

Most architecture diagrams organise by component. This one organises by how long each thing lives, because that is the only axis Q1 actually turns on. Notice which shapes cross the block boundary and which ones stop dead at it.

Reading it in one sentence: the top band is disposable and the bands below it are not, so the fix is to make sure nothing you need is only in the top band. The teal arrow is the entire transition, one function reading one store and writing a sentence into a new session's instructions.

What gets sent, and what deliberately does not

The reseed is a short structured summary, never the raw transcript. It is generated by a plain function reading CallState. Three branches, depending on how far the caller actually got: 

// a value validated, and they already confirmed it out loud
"This call is continuing from an earlier block. The caller already provided
 their policy_id, and it has already been validated as BN742D. Do not ask
 for it again. They already confirmed it verbally — do not read it back again."

// validated, but not yet confirmed — different instruction
"...validated as BN742D. Do not ask for it again. They have not yet verbally
 confirmed it — read it back once, then confirm, before continuing."

// mid-capture, nothing validated
"...The caller was in the middle of providing their policy_id at Tier 2 but
 had not completed it. Continue from there — do not restart with a fresh greeting."

Notice the second branch. The state carries not just a value but how much that value has been through, and the instruction changes accordingly. Losing that distinction would mean either re-reading a value the caller already confirmed, or acting on one they never did.

The three things this deliberately is not

These are constraints in the code, not accidents, and each one is worth being able to defend:

1. It does not replay what the caller said. Cost and latency scale with transcript length, and worse, a model handed old dialogue can misread past phrasing as a new instruction.

2. It never claims the caller confirmed something CallState does not say they confirmed. The preamble cannot invent provenance, because it is generated from structured fields rather than written by a model summarising a conversation.

3. It never asks the new session to trust anything except what the orchestrator itself already decided. The new session is handed a conclusion, not a memory to re-interpret.

And the tone problem, which is the part teams miss

The data usually does carry over fine. What breaks the illusion is that the new block fires its default greeting anyway. "Hello, how can I help you today?" Nothing was lost, but to the caller it sounds like everything was. That is why every branch of the preamble ends with an explicit behavioural instruction, not just facts: Do not ask for it again, do not restart with a fresh greeting.

Where the state actually lives

Originally CallState was an in-memory Map. That survives a session closing, which is what Q1 asks about, but it does not survive the process itself dying. So it was extended: CallState, the audit log, and captured audio now also write to disk, and a brand new connection can rebuild a call from those files with nothing in memory. That is the harder version of the same claim, and it matters for the disclaimer below.

That answer changes which half of this work is even needed, so it is worth settling before building the store.

Q2

Who owns barge-in

The positional problem, before the technical one

Barge-in is the caller talking while the bot is mid-sentence, and the system stopping to listen. Before any of the mechanism matters, notice why they cannot do it today: with the Realtime session wired straight to the SIP leg, the caller's audio goes to OpenAI and their own code is not in that path. You cannot interrupt a conversation you are not part of.

Moving to WebSocket is not interesting because of the protocol. It is interesting because of where it lets you sit. Every frame now passes through code you control, in both directions, which is what makes every mechanism below possible.

The two clocks, and why this breaks silently

Here is the part that catches teams out, and it is the single most useful thing to be able to explain about Q2.

When the model produces a response, audio arrives from the API far faster than it plays. Generation of a five second sentence can finish in well under a second. So response.done fires, and the model is finished, while the caller is still four seconds from hearing the end of it.

That means "is the model still generating?" and "is the caller still hearing something?" are two different clocks, and they disagree for most of every response. Gate your barge-in on the wrong one and it does nothing at all for the majority of the audible sentence, while looking completely correct in the code.

Two clocks

The bot begins a five second read-back. Two things start at once: OpenAI generating the audio, and the caller actually hearing it. They do not run at the same speed.

Who decides what, in order

The model is not stripped of its role. It keeps the one job it is well positioned for, noticing that speech started. Everything downstream of that signal belongs to the relay.

Steps 2 and 3 of that diagram, as they actually run — cancel only if a response is still generating, but tell the browser to stop unconditionally, because generation finishing tells you nothing about whether the caller is still hearing it:

poc/apps/be/src/relay/relay.ts — handleUpstreamEvent(), abridged
if (type === "input_audio_buffer.speech_started") {
  // Cancel upstream ONLY if the model is still generating. Cancelling a
  // finished response is what produced "response_cancel_not_active".
  if (this.responseInFlight) {
    this.upstream?.cancelResponse();
    this.responseInFlight = false;
    if (this.currentResponseId) this.cancelledResponses.add(this.currentResponseId);
  }

  // Tell the browser to stop playback regardless of whether generation
  // finished. Gating this on responseInFlight meant that for most of the
  // audible response a barge-in did nothing at all.
  this.pendingTruncateItemId = this.currentItemId;
  this.toBrowser({ type: "interrupted" });
  this.toBrowser({ type: "turn-state", assistantSpeaking: false });
}

Why truncation is not optional

Cancelling stops the model generating more. It does not correct what the model believes it already said. Left alone, the session history contains the full sentence, so later in the call the bot will reference something the caller never heard, with complete confidence.

So step 5 rewrites history to match reality: conversation.item.truncate with audio_end_ms set to the number the browser reported. The model's record now ends where the caller's ears did.

poc/apps/be/src/relay/relay.ts — case "played-ms", abridged
const itemId = this.pendingTruncateItemId;
this.pendingTruncateItemId = null;
const heardMs = Math.max(0, Math.round(msg.ms));
if (!itemId || heardMs === 0) break;  // nothing was playing — not a barge-in

this.upstream?.send({
  type: "conversation.item.truncate",
  item_id: itemId,
  content_index: 0,
  audio_end_ms: heardMs,
});
this.audit({
  authority: "index-only",
  kind: "note",
  summary: `Caller barged in — playback stopped and history truncated to ${heardMs} ms`,
});
Two details that were real bugs

Stale audio already on the wire. Cancelling upstream does not recall frames already sent. Without dropping deltas belonging to a cancelled response, a burst of audio plays after the interruption and undoes it. The relay tracks cancelled response ids and discards their audio.

The truncate target must be a message item. A response often emits a function_call item first, which carries no audio. Naming that as the truncate target returns Only model output audio messages can be truncated.

Zero milliseconds is not a barge-in

One more piece of judgement the relay keeps for itself. speech_started fires whenever the caller talks, including when the bot is silent and they are simply taking their turn. The relay cannot tell those apart, so it does not try. It asks the browser, and if the answer is played-ms: 0, nothing was playing, nothing gets truncated, and nothing is logged as an interruption. The distinction is drawn from evidence rather than guessed at.

That number comes from the browser's own scheduling clock, not a guess or a timer race. If the last scheduled buffer already ended before now, nothing was playing, full stop:

poc/apps/fe/src/lib/audio-player.ts — AudioPlayer, abridged
interrupt(): number {
  // `cursor` is the context-clock time the last scheduled buffer ends —
  // an exact, synchronous answer to "is audio still playing?", unlike
  // the `scheduled` array, which is pruned a tick late by onended.
  const stillPlaying = this.ctx !== null && this.cursor > this.ctx.currentTime;
  const played = stillPlaying ? this.playedMs() : 0;

  for (const source of this.scheduled) {
    try { source.stop(); } catch { /* already stopped — fine */ }
  }
  this.scheduled = [];
  return played;  // 0 here is what tells the relay "not a barge-in"
}

"The caller" is a browser tab with a clean microphone at 24 kHz. A real SIP leg at 8 kHz, with line noise, echo, and a codec. Detection sensitivity tuned against a clean mic will not transfer unchanged.
The browser measures playback and reports played-ms. Whatever terminates the media, an SBC or media bridge, has to measure and report the same number. The mechanism depends on that component existing and being honest about it.

The honest limit: we do not have benchmarked interruption numbers at their call volume. The architecture is sound and the mechanism is real running code, but the sensitivity tuning, how aggressive versus how forgiving, needs testing against their own recorded call audio. That is a measurement job, not a design job.

Q3

Handing off to a human

The bar for success is narrower than it sounds

This is easy to over-engineer, so it is worth naming the actual bar first: a handoff feels broken at exactly one moment, when the human agent asks the caller for something the bot already has. Everything below exists to make that moment structurally impossible, not to build a bigger summary.

It shares Q1's whole architecture. The orchestrator holds state; here the receiving end is a human's screen instead of another AI session. If Q1's answer is already built, Q3 is mostly that same state read out for a different audience.

Two triggers, both deterministic, watch the handoffFired latch

Neither trigger below is inferred from tone or from the model deciding the call "seems" stuck. Both are plain conditions on CallState, checked the same way every time.

That latch is not decoration. Before it existed, a tier-exhausted handoff could fire, and then the model would separately call request_handoff on the very next turn, silently overwriting tiers-exhausted with caller-request, the correct reason replaced by an incorrect one. A call now hands off at most once, whichever reason got there first.

What actually gets handed over

Reading the code is more convincing than describing it, so here is the real assembly, not a paraphrase. Everything on the right already existed before the handoff, this function computes nothing new: 

buildHandoffPacket(state, reason) {
  // deterministic template — never model-generated
  summary: [
    `Caller was providing ${state.field}.`,
    `Reached Tier ${state.tier} (${TIER_LABEL[state.tier]}).`,
    state.confirmationState === "confirmed"
      ? `${state.validatedValue} was validated and verbally confirmed.`
      : `${state.validatedValue} was validated but NOT yet verbally confirmed — confirm before acting on it.`,
    REASON_LABEL[reason],
  ].join(" "),

  matchedRecord:   findPolicy(state.validatedValue),   // from Q5's ladder
  auditEntryCount: getAudit(state.callId).length,       // from Q6's log
  audioAvailable:  isRecordingEnabled(state.callId),    // from Q6's toggle
}

Notice the confirmed-versus-not branch again, the same distinction Q1's reseed cared about. A value that is validated but not confirmed is a materially different thing to hand a human than one the caller has verbally agreed to, and the template says so explicitly rather than collapsing both into "captured".

Delivery is a platform question, not a data question

The packet above is delivery-agnostic on purpose. How it actually reaches a human depends entirely on what is on the other end, and there are three real shapes this takes:

SIP headers are not built to carry a summary, so that path deliberately passes only a reference id and leaves the lookup to the receiving system. Whisper transfer trades the visual packet for a few spoken sentences played to the agent alone before the caller connects. None of the three is more "correct"; each is the answer to a different platform's constraint.

Q4

Grounding in a knowledge base

Not a binary, three techniques layered

Framed as "fetch before the model responds, or let it call a tool", but the production answer layers three things. Tool-calling is the default, most turns need no lookup at all. Preload the hot facts into session instructions for zero-latency answers to the common questions. And cover whatever latency remains with speech, "let me check that for you," said immediately while the lookup runs, because voice has no typing indicator and silence just sounds like the call hung.

That third piece is a recommendation, not something built here, flagged plainly in the disclaimer below. What is built, and worth going under the hood on, is the tool call itself: a real deterministic search, not an API mock.

Why keyword search, not embeddings

This is a deliberate choice worth being able to defend, because "why not just use embeddings" is a fair question to get asked. Q4's actual claim is that the model never answers from its own training, it only ever repeats back what the search returns. A similarity score from an opaque embedding model would not break that claim, but it would make it unverifiable, you would be trusting a second black box instead of the first one. A keyword match with a visible score is checkable by anyone reading the payload.

The regression, live

This is the single most fragile test in the suite, and the reason is worth seeing mechanically rather than taking on faith. Step through what "what is the capital of France" actually does to the search.

Anchor-gated search

A caller asks something the knowledge base has nothing to do with. Watch what a naive tokenizer does with the word "the".

"What is the capital of France?"
kb-grace-period · Grace period for premium payments
anchor (title + keywords)
body (article content) …"payment is not received by the policy lapses"…

Two independent defenses are doing work here, and the bug only fully dies when both exist. Stopwords stop "the" from ever becoming a query token in the first place. The anchor gate, requiring at least one hit against an article's title or hand-written keywords before its body text can even be considered, means that even a token that slips past the stopword list cannot qualify an article on body text alone. Body text only re-ranks between articles that already qualified through the anchor.

Contrast that with a question the knowledge base actually answers. "What's the grace period if I pay late?" tokenizes to grace, period, pay, late. Against the same article, grace and period and late all hit the anchor directly, pay matches nothing exactly, because the keyword is "late payment," not "pay". anchorHits: 3, comfortably over the gate, and this time correctly grounded.

What the model is actually handed

Same guardrail shape as everywhere else in this build: a status, and either the exact source content or an explicit instruction to admit it does not know. Never a paraphrase the model could drift from, never silent permission to fill a gap from its own training. 

// grounded — the model gets the real article, not a summary of it
{
  "status": "grounded",
  "articles": [{ "title": "Grace period for premium payments", "content": "…" }],
  "instruction": "Answer using only the content above, in your own words, and
                mention which topic it's from."
}

// no_match — nothing to draw on, and the instruction says so plainly
{
  "status": "no_match",
  "instruction": "Say plainly that you don't have that information on file,
                and offer to have someone follow up. Do not guess."
}

The pre-speech guard from Q3's audit trail shows up here too, unchanged in shape: a search fired before the caller has said anything gets discarded the same way a premature capture does, same root cause, same shared fix, applied twice rather than duplicated.

Q5

Capturing structured and alphanumeric values

This is the core of the whole build. Every other question's page is a view onto machinery this one exercises, the audit trail (Q6) is watching this ladder run, the guardrails (Q7) are this ladder's payloads inspected, the barge-in demo (Q2) interrupts this ladder mid-read-back. Worth the most depth, because it is the part most likely to get a genuinely technical follow-up question.

The fact worth having ready

"So just fix the codec" is a fair question to expect, and the honest answer routes through a distinction, not a single explanation. Stop consonants (B/P, D/T) and sibilants (S/F/X) are confused because 8 kHz genuinely discards the high-frequency detail that separates them. Wideband audio fixes both classes.

It does not fix nasals (M/N). Nasals live in low frequencies a narrowband line carries fine, they get confused because the mouth shape producing them is nearly identical, a fundamentally different mechanism that survives a codec upgrade untouched. That is why NATO disambiguation earns a permanent place in the design even in a hypothetical wideband future, not just a workaround for today's phone lines.

The ladder, running for real

Cheapest check first is not a principle stated in a comment, it is the literal control flow. Watch the lookup step specifically, on a bad-format value it never runs at all.

runValidationLadder

Three real attempts, in the order a caller might actually produce them.

"banana banana banana"
0 · normalize – trim, uppercase, strip spaces
1 · regex – ^[A-Z]{2}\d{3}[A-Z]$
2 · lookup – a real database read — the only step with a network cost

Escalation, the whole function

This is genuinely the entire escalation policy, no retry counter, no patience threshold, no sentiment score anywhere in it. One failed attempt is sufficient, and there is nowhere further to go past 3 today: 

function nextTierFor(valid: boolean, tier: Tier): Tier {
  if (valid) return tier;        // success never moves the tier
  if (tier === 1) return 2;      // one failure is enough
  if (tier === 2) return 3;
  return tier;                   // Tier 4 (SMS/web) isn't built — see disclaimer
}

That is the argument for "escalation is silent, never a confession of failure" made concrete: there is no counter to consult, no threshold to tune. A single deterministic branch, and the caller never hears "sorry, I didn't get that", the bot just starts asking for spelling.

Tier 3: a real state machine, not a lookup table

Multi-tap decoding needs to track more than "which key was pressed". The same key pressed twice quickly means one letter cycling; the same key pressed twice with a pause means two separate letters. That distinction needs a timer, not just a keypress handler.

Entering "B" needs the 2nd letter on key 2, which means three taps on the same key.

Q6

Knowing what the model actually heard

Worth conceding plainly before anything else, because it buys the authority to be firm on everything that follows: this is a real architectural gap, not a misconfiguration. A speech-to-speech model does not hand you a text record of what it understood. Teams run a separate transcription, often a different model, on the same audio, and now two systems that both listened may disagree about what happened.

The fix is not a setting. It is refusing to let every record be treated the same way.

Enforcement, not a taxonomy

The three classes below are not a policy written in a doc that people are supposed to remember. They are a TypeScript field with no default value: 

export interface WriteAuditInput {
  callId: string;
  authority: RecordAuthority;   // required — no default anywhere
  kind: AuditEntry["kind"];
  summary: string;
  payload?: unknown;
}

Every single call to writeAudit(), and there are more than a dozen of them across the codebase, must state which class the entry belongs to. Omitting it is not a runtime warning, it does not compile. That is the actual mechanism behind "the mistake cannot happen silently", not a reviewer's discipline, a type the compiler refuses to accept incomplete.

ground-truthraw audio / keypresses — the only class that can settle a dispute
authoritativetool-call arguments — the model's own structured understanding, no second listener
index-onlya separate transcript — useful to find a moment, never evidence

The toggle, under the hood

Ground truth used to mean, in this build, only DTMF keypresses, a real signal, but a narrow one. Raw audio is now genuinely captured, opt-in, off by default. Watch what "off" actually means at the point of writing, not at the UI layer.

persistAuditEntry(), two calls

Two identical calls, differing in one respect: whether "Record this call" was checked before Start.

Call B Record this call: on

The gate is not a UI-layer filter hiding a folder that exists anyway. It sits inside persistAuditEntry() and persistCallState() themselves: if (!isRecordingEnabled(callId)) return;, before ensureCallDir() even runs. For a call with the toggle off, no directory is ever created, this was verified directly against the real filesystem, not assumed from reading the code.

Why the cache still gets everything

The in-memory cache in audit-store.ts is written unconditionally, regardless of the toggle, that is what the live wire log the browser watches during a call is reading from. Only the durable copy on disk is gated. The toggle decides whether the record survives the call, not whether the call has a live audit trail while it is happening.

The free audit trail nobody has to build

One more thing worth having ready, because it costs nothing extra: a spoken confirmation is itself evidence. "Your policy ID is B-N-7-4-2-D, is that right?" followed by "yes", recorded, is a validated record on its own. No transcription model, no extra infrastructure, it already exists the moment Q5's read-back happens.

Q7

Guarantees inside a free-form conversation

Three layers, strongest first, already introduced. Worth going under the hood on two of them specifically: what "structurally impossible" looks like as actual syntax, and a guardrail this build has that goes further than a status flag, a confirmation with an expiry clock.

Layer 1, made literal

"The model has no path to a validated signal unless the system genuinely validated" is not a design intention. It is the shape of one ternary: 

const modelPayload = outcome.valid
  ? {
      status: "validated",
      say_verbatim: outcome.normalizedValue.split("").join("-"),  // only exists here
      instruction: "Read this back once, character by character, then confirm."
    }
  : {
      status: "invalid",
      instruction: "Do not tell the caller what you heard. Ask them to try again."
      // say_verbatim is not merely empty — the field does not exist in this branch
    };

There is no code path where say_verbatim is present and outcome.valid is false. Not a check that could be bypassed, a field that is syntactically absent from the object literal in the branch where it would be wrong. And notice where the string comes from: built fresh from outcome.normalizedValue at the moment of the payload, never recalled from something said turns ago. That is the tool-call pattern run in reverse, instead of the model handing you structured data, you hand it structured data, right before the one moment it needs to be exact.

Q8

Version pinning and rollback

Q1's whole property pays off a second time here, and it is worth saying that connection out loud: rollback is safe and instant specifically because call state lives in the orchestrator, never in the model. Switching which model the next session talks to loses nothing, because nothing worth keeping was ever stored inside a session to begin with.

The gate is one function, and it does not check what you might expect

Worth reading exactly, because it holds a detail easy to assume incorrectly from the UI alone: 

export function activateVersion(id: string): ActivateResult {
  const version = modelVersionsData.versions.find(v => v.id === id);
  if (!version) return { ok: false, reason: `Unknown model version: ${id}` };

  const regression = regressionSuiteData.suites[id];
  if (!regression) return { ok: false, reason: `No regression suite result on file for ${id}` };
  if (regression.failed > 0) {
    return { ok: false, reason: `Blocked: ${regression.failed} of ${regression.total}
      regression tests are failing for ${id}...` };
  }

  activeModel = id;   // the entire effect of a successful activation
  return { ok: true, active: activeModel };
}

Notice what is not checked. The dashboard shows a "production / candidate / deprecated" status on every row, but this function never reads that field. The only thing that blocks activation is regression.failed > 0. In this build's fixture data the deprecated preview happens to also have 12 failing tests, so the two signals agree by coincidence, not by the gate enforcing lifecycle status. The status label is informational, the regression count is the actual lock.

getActiveModel() is read at the exact moment a new upstream WebSocket opens, the same call site that logs Upstream session opened against ${getActiveModel()} for every session in this build, including Q1's block-transition reseeds. Q9

Half-cascade versus full speech-to-speech

Read this before the rest of the section Every other question on this page walked through real, running code. This one does not, because there is none to walk through. No page, no shadow-mode logging, nothing. What follows is architecture and a decision framework, and it is written to look different from the eight sections above it on purpose, so it is never mistaken for a demo.

Two pipeline shapes, not two settings

Full speech-to-speech has exactly one hop: audio in, one model, audio out. Nothing sits between the model deciding what to say and the caller hearing it, which is what makes it fast and natural, and also what makes it unreviewable, there is no point in the pipeline where anyone else gets a look. Half-cascade is not a flag on that pipeline, it is a structurally different one.

What "shadow mode" today actually is, and precisely is not

Requesting both text and audio modalities from the Realtime API gets you a text stream alongside the spoken output. That is real and available right now, no build required. It is also not on the diagram above, because it does not belong to either pipeline, it does not sit in the audio path at all.

both streams begin at the same instant
audio stream
text stream

They race, they do not queue behind each other. By the time text has arrived and could be read by a checkpoint, the matching audio bytes are already generated, in most implementations already sent. There is nothing left to stop. What this mode is genuinely good for is logging what a checkpoint would have vetoed, real signal for deciding where a true veto is worth building, but calling it a review gate would be describing a capability that does not exist.

The decision framework, same shape as Q7

We do not have verifiable production numbers at Acme's volume, and it is better to say so than hand over a figure that cannot be backed up. What transfers directly from Q7 is the scoping principle: do not apply half-cascade to the whole conversation. Scope it to turns that actually need a veto, compliance-sensitive statements, critical confirmations, full speech-to-speech everywhere else. Paying the cost on routine chit-chat that never needed reviewing is the same blanket-rigidity mistake as Q7's, applied to infrastructure instead of prompts.

And the way to find that scope is empirical, not argued: instrument the checkpoint once it exists, log how often it actually triggers a rewrite. Rewrites clustering in a narrow category is the evidence for scoping narrowly. Rewrites spread wide is the evidence the broader cost is worth paying. Either way the answer comes from Acme's own instrumentation, not a benchmark slide.
